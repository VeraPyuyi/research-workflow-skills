# Define a Useful Research Tool or Product

Read the [shared contract](../research-navigate/references/workflow-contract.md).
Select [domain references](../research-navigate/references/domains/index.md) only
for scientific capabilities or claims actually used by the proposed product.
Use [model routing](../research-navigate/references/model-routing.md) only when dispatching work to more than one model;
then use it for a free
need/alternatives branch and independent evidence review.

An independent practical tool does not need a paper. An existing paper does not
by itself establish demand for a product.

## Turn the opportunity into a bounded decision

1. Inspect supplied assets, workflows, user feedback and existing alternatives.
   Identify who has the problem, in what situation, how often, and with what
   current cost or friction. Distinguish observed need from assumptions.
2. Compare reuse or extension of existing tools with a new product. Explain the
   concrete benefit, required research capability and limits of its evidence.
3. Define the smallest useful end-to-end journey, inputs/outputs, supported cases,
   exclusions and a measurable acceptance example. Choose technology only when the
   project requires that decision; retain existing conventions when suitable.
4. Define a modest user-validation plan using supplied or authorized evidence.
   Record whether testing is with actual users, the requester, simulation or
   hypothesis. Do not convert a simulated walkthrough into user testimony.
5. Estimate effort/resources, distribution goals, maintenance expectations and
   reasons to stop or revise. Identify assumptions that the MVP should test.

## Deliver and finish

Deliver a product brief with target user/job, need evidence, alternatives, value,
MVP boundary, research/rights constraints, acceptance, validation, resources and
open decisions. Include the shared handoff and product/MVP approval package.
Existing approval covering this scope is sufficient to route to product-build.

Example: a local experiment-reporting utility can start with one recurrent user
workflow and a representative input/output fixture. Describe wider demand as
unknown until evidence supports it.

# Maintain the Research Main Line

Protect the importance of the research question, not a preferred answer or tool.
Keep a stable broad theme and an evidence-adjustable paper thesis. This is a
cross-stage responsibility, not a new experiment or mandatory review after edits.

Read the [shared contract](../research-navigate/references/workflow-contract.md)
and, only when dispatching to more than one model, [model routing](../research-navigate/references/model-routing.md).
Use [the thesis anchor protocol](references/thesis-anchor.md) to establish or
revise the project record, assess cumulative drift, or prepare a corrective handoff.

## Establish the anchor

Recover original user requests, later explicit choices and the existing brief.
Record source locations, what was actually read, and gaps. A recent manuscript,
chat title or latest handoff cannot by itself establish the original user intent.

Keep `research_focus` in the existing project state, or link its designated
artifact there (default `research/focus/anchor.md`, referenced from
`research/STATE.json`). Stage packages carry only the three-to-five-line reminder
below, not this skill. At each milestone, record a short table mapping the
title and headline claims to the `theme_envelope`; run the full drift review
only when that table changes. Separate:

- `theme_envelope`: the core phenomenon, scientific importance, audience/use,
  explicit boundaries and instruction provenance. Changes require an explicit
  user decision; preserve previous versions.
- `active_thesis`: the current question, intended contribution, evidence gap,
  connection to that theme and version. With in-theme delegation, evidence-backed
  changes within existing authority and resources can proceed autonomously.

Do not invent user confirmation or turn inferred preferences into hard boundaries.
Missing history is an explicit provenance gap; continue clearly covered work.

## At a handoff or meaningful choice

Compare the next work with both the original theme and the cumulative pivot
history. State which important question it answers and what evidence could change
understanding, method design or use. Classify it as `on-spine`,
`in-theme-pivot`, `auxiliary-only`, or `out-of-theme-drift`. Keep classification,
evidence status and execution status separate; an in-theme claim is not thereby true.

For borrowed theory, experiments or engineering, map
`tool_or_subtask -> target_object_in_theme -> main_claim_served`.
An auxiliary result gets a limited role, bounded effort from existing resources
and a return condition. Ease, polished code, available GPUs, a better proxy metric
or an attractive theorem is not a reason to lower the contribution requirement.

Record a short reminder in the next scientific worker package: theme/version,
current thesis/version, this task's claim link, boundaries and return condition.
No extra agent, Jev call, full test suite or report is needed for routine reminders.
The coordinator maintains one shared version; branches return proposals.
Do not attach these private reminders or history to a blind venue-review packet.

## Correct drift and continue

- On-spine work proceeds under existing authority.
- An in-theme pivot records the old/new question, evidence, value, affected
  definitions/results/checks and resource impact; reopen only affected coverage.
  A new method or a credible negative/boundary finding need not reopen topic approval.
- Auxiliary work remains supporting evidence, a lemma, control, appendix or
  separately queued product idea. Return to the scientific dependency after its
  bounded task; it does not silently become the paper's headline.
- Out-of-theme work or a violated explicit boundary needs a concrete user decision
  before that change. Preserve the proposal and keep independent on-theme work moving.
  A resource expansion still needs its applicable approval even when on-theme.

Scientific value may be a reliable gain, explanation, negative result, counterexample,
boundary or useful benchmark. Never manufacture a positive answer, suppress adverse
evidence, or keep an uninformative project alive solely to preserve its theme.
If no valuable feasible in-theme path remains, explain closure or a proposed new
theme with evidence and bounded alternatives; do not silently substitute an easier paper.

## At M1-M5 and delivery

Consolidate cumulative alignment with the existing milestone checks. In internal
review, compare the whole argument and headline claims with the theme and actual
evidence. For M4/M5, the author-side coordinator performs this comparison; fresh
reviewers judge only the submitted materials and verified venue criteria.

Deliver the updated anchor or alignment note, inspected provenance, remaining gaps,
branch dispositions, and a concrete next scientific action with authority/status.
`research-analyze` evaluates contribution strength, `research-navigate` dispatches,
and `research-optimize` improves execution. Focus bookkeeping and optimizer
completion never trigger each other or create recurring optimizer events.

## Mathematical work when applicable

Keep the original scientific problem as the reference when local mathematics expands. Check the hardest remaining obstacle and cumulative changes; a correct easier surrogate is not automatically the original contribution.
Read [mathematical work](../research-navigate/references/mathematical-work.md) for the optional record and return contract.
